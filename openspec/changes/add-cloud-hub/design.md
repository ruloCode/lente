# Design

## Context

The hub is a single Node process with TCP (clip) and HTTP/SSE (phone). Cloud platforms generally expose HTTP(S) and WebSocket ingress, not raw TCP. Whether Modal's web endpoints support long-lived WebSocket and SSE connections for a custom Node container, and how its volumes behave across deploys, is **not yet verified**: task 1.1 is a spike that settles it before anything else is built. MentraOS's audio path (primary transport plus a WebSocket fallback with the same server code) informed the "same frames, two transports" choice.

## Goals / Non-Goals

**Goals:**
- One hub codebase that runs on the laptop and in the cloud with configuration only.

**Non-Goals:**
- Multi-tenant hosting.

## Decisions

1. **Same frames over WebSocket.** The message layer from `harden-clip-protocol` is transport-agnostic; the WebSocket path wraps it. Alternative: a different cloud protocol; rejected to keep one tested contract.
2. **WebSocket server without a dependency if it stays small.** RFC 6455 server framing for binary messages is a contained piece of code with tests; if the spike shows TLS termination and upgrades are handled by the platform, the hub only needs the upgrade handshake and framing. Otherwise adopt a well-known WebSocket package and record why.
3. **Firmware WebSocket client over TLS.** Candidate: the ESP32 core's TLS client with a small framing layer, or a widely used Arduino WebSocket library; decided in the spike by flash size and stability over 30 minutes.
4. **Tokens, not accounts.** Device tokens and a phone pairing code generated by the hub, stored in the persistent volume; revocation by deleting the token.
5. **Fallback stays local.** If the cloud is down, the clip can still be pointed at a laptop hub on the LAN.

## Risks / Trade-offs

- [Platform does not suit long-lived sockets] → the spike decides early; alternative hosts considered then.
- [Latency from the cloud region] → measured in evals (clip → hub stage) and compared with the LAN.
- [Cost of an always-on container] → measured against the USD 100 credit; scale to zero outside demo hours if needed.

## Migration Plan

1. Spike on Modal with a WebSocket echo and SSE.
2. Deploy the hub with secrets and a volume; point the emulator at it.
3. Flash a clip build that targets the cloud hub; keep a LAN build for fallback.
